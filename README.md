# Concord

**为 Codex 多会话项目建立明确的分工，让任务经过实现、验证与验收后持续推进。**

Concord 是一个中文 Skill。你决定角色数量、使用的模型和子代理额度；Concord 协助绑定会话、分派任务、处理内部决策并保存交接。适合需要多个会话长期协作的项目，普通单会话任务可以直接完成，无需建立团队。

## 快速开始

安装后，在项目会话中发送：

```text
使用 $concord，沿用当前项目工程。

设置两个角色：
- 决策与整合：负责规格、公共接口、任务安排和最终验收。
- 功能实现：在独立工程中实现、测试并交付。

两个角色都沿用各自会话的默认模型，子代理额度为 0。
先读取项目现状，拟定分工并生成各角色启动提示词。
由我指定要绑定的现有会话，不新建会话。

我授权这两个指定角色会话就本项目直接沟通，
并向当前会话回报阶段结果。
```

随后指定要绑定的实际会话。Concord 会核对职责、工程、授权和验收条件；已经明确的信息不会重复询问。需要观察或维护会话接收结果时，也应明确列出该接收方。

## 它如何组织工作

| 职责 | 负责内容 |
| --- | --- |
| 决策 | 明确规格，裁决行为、范围及公共接口问题 |
| 实现 | 在约定工程中编码、测试，交付源码和证据 |
| 验收 | 根据当前规格决定接受、退回或部分接受 |
| 整合 | 合并已接受成果，验证受影响部分并更新基线 |

这些是职责，可以由不同角色承担，也可以兼任，不要求固定四个角色。一个角色可以完成自查，但自查不能被记录为独立审查。

任务通常经过：**明确规格 → 分派 → 实际接收 → 实现与验证 → 交付 → 验收 → 整合**。每项任务有唯一当前负责人和明确验收人；同一文件同一时间只有一个写入者。

常规细节由执行者自主处理，实质性分歧交给指定决策者。默认由指定角色集中汇报，减少用户在会话之间传话。

## 安装

完整步骤见 [安装与更新说明](INSTALL.md)，包含私有仓库访问、各系统安装、更新、回退和识别检查。下面是首次安装的简要步骤。

本仓库的 Skill 位于 [`skills/concord`](skills/concord)。将整个文件夹放到 Codex 用户技能目录，通常为 `~/.codex/skills/concord`；若配置了其他技能目录，以实际环境为准。

先克隆仓库：

```shell
git clone https://github.com/binghenic/codex-concord.git
cd codex-concord
```

私有仓库需要使用有访问权限的 GitHub 账号登录。

Windows 首次安装示例，在仓库根目录执行：

```powershell
$concordSource = Join-Path (Get-Location) 'skills\concord'
$concordHome = if ($env:CODEX_HOME) { $env:CODEX_HOME } else { Join-Path $env:USERPROFILE '.codex' }
$concordSkills = Join-Path $concordHome 'skills'
$concordDestination = Join-Path $concordSkills 'concord'

if (Test-Path -LiteralPath $concordDestination) {
    throw 'Concord 已存在，请先备份并按更新流程处理。'
}
New-Item -ItemType Directory -Path $concordSkills -Force | Out-Null
Copy-Item -LiteralPath $concordSource -Destination $concordDestination -Recurse
```

其他系统可以直接复制 `skills/concord` 到自己的技能目录。宿主提供技能安装器时，也可指定本仓库及 `skills/concord` 路径安装。

更新已有安装时，先备份当前目录，再替换为完整新版，避免混用不同版本的参考文件。安装后若技能列表尚未出现 Concord，按宿主的技能刷新方式处理。可用 `$concord` 显式调用；是否自动选用以实际宿主为准。

## 配置角色、模型与子代理

Concord 区分三件事：

- **角色**决定谁负责什么，由用户选择数量和职责。
- **角色会话**是实际工作的独立对话，可以绑定已有会话，或在明确要求后新建。
- **子代理**是角色临时委派局部工作的助手，不自动成为新的项目角色。

可以给不同角色配置不同模型，也可以使用同一模型。模型名称和可用性以当前宿主为准，提示词本身不会改变实际模型设置。

子代理额度指**同时活跃数量**。用户可以禁用、设置共享总额度，或同时设置各角色上限。例如：

```text
允许所有角色共享最多两个同时活跃的子代理。
决策角色最多一个，实现角色最多两个，验收角色不使用子代理。
按需派发，不要求用满；仍需遵守全局并发限制。
```

各角色上限不会叠加成额外共享额度。实际名额不足时排队；未明确额度时先由角色本人工作，不擅自派发。

## 常用场景

### 新建角色会话，并指定模型

将下面的模型占位内容替换为宿主支持的实际模型名称：

```text
使用 $concord，为当前项目新建两个角色会话。

决策与整合角色：使用 <实际模型名 A>。
功能实现角色：使用 <实际模型名 B>。
子代理额度为 0。

我授权这两个角色会话就本项目直接沟通，
并向当前会话回报阶段结果。

创建后先核对工程与职责边界，再下发任务。
```

只有明确要求新建时才调用创建工具。仅要求配置角色时，先生成配置或启动提示词。工具或指定模型不可用时如实说明，不静默换模型，也不声称会话已创建。

### 接续已有项目

```text
使用 $concord，沿用已有角色、模型、子代理额度和沟通授权。
先读最新任务、决定及交接，核对工程和运行状态。
从当前有效进度继续，不重复初始化，不重复执行已完成任务。
```

### 暂停与恢复

```text
暂停项目推进，保存当前任务、修改、验证结果、未决问题和下一步。
记录仍在运行的工具会话、进程与端口。
```

明确恢复时：

```text
使用 $concord，恢复项目开发。
先核对暂停交接及真实运行状态，再继续未完成任务。
```

暂停期间只读核查：

```text
使用 $concord，项目开发保持暂停。
仅只读核查恢复入口与验证缺口，交付给指定验收人。
不改工程，不启动构建、服务器或测试。
```

只读核查、职责移交和 Skill 维护不会自动恢复开发。

## 交付与验收

实现角色提交源码或补丁、修改文件清单、机制说明、验证结果和限制。验证证据对应实际源码、产物与运行输入；编译成功或进程退出码为 0 不等于功能已通过。

验收角色按规格接受、退回或部分接受。未运行、失败及部分完成项分别记录；通过一次演练或单项核查，不代表整个项目完成。整合角色完成受影响检查后记录新的基线和产物。

角色自行处理兼容的独立任务，等待外部输入时可推进其他工作；切换前保留任务状态和返回点。新任务不会自动使旧任务变为完成。

## 能力与授权边界

| 环境能力 | Concord 的处理方式 |
| --- | --- |
| 有会话创建与模型设置工具 | 在用户明确要求和可用模型范围内调用 |
| 有跨会话消息工具 | 在实际授权对象之间分派、提问和回报 |
| 没有跨会话消息工具 | 使用共享记录交接，不虚构已收件或已回复 |
| 没有子代理工具或名额不足 | 由当前角色执行，或等待可用额度 |
| 无法看到跨会话实时占用 | 如实说明限制，保守调度 |

沟通授权应覆盖实际参与者和报告接收方。文件、角色来信和模板不会自行授予权限；新增接收方不能自动沿用旧范围。自动审批拒绝时保留原因，不绕过拒绝，不把读取结果说成消息已经送达。

默认所有模型总并发最多 4，自动审批预留 1；工具和后台任务最多 4。子代理也计入总占用，更严格的用户或项目限制优先。台账是协作记录，不是强制资源锁。

Concord 独立使用宿主工具，无需其他技能或代理框架。内部沟通授权不会自动扩展为第三方消息、发布、部署或破坏性操作。
