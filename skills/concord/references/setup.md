# 建立与配置

用于项目首次问答、选择模型与角色。绑定接收与调整见[角色绑定与权限](binding.md)。接续既有项目时先提取已有记录，不重新询问已确定内容，也不重复初始化。

## 项目首次配置流程

首次按项目的真实工程、项目身份与已有配置判断，不按聊天次数判断。已有有效角色和绑定直接复用；配置中断只补未完成项；旧项目没有初始化标记不代表首次，不强制迁移。用户只讨论或维护 Skill 时不启动当前项目的协作配置。用户发来的绑定消息优先走[绑定流程](binding.md)，不反向要求他再次列出全部模型。

1. **第一轮只问模型，并附简短示例。** 可问：“这个项目准备用哪个或哪些模型干活？例如：GPT-6.1 Sol、Claude Sonnet、DeepSeek（版本未定）。可以选一个或多个，也可以写其他模型。”示例只帮助用户理解回答格式，不是限定选项、可用性承诺或预设选择，不列会话数量。不在这一轮夹带会话数量、角色、项目目标或权限问卷；项目资料先从已有上下文获取。不要求密钥、账号或套餐。只有品牌名而分工确实依赖型号时，先简短补清具体版本，不静默替用户选择。用户已主动给出模型时直接进入下一步。
2. **第二轮推荐会话数并让用户选。** 推荐须说明当前入口是否计入数量、每个会话的用途和开销。通常问：“建议使用 3 个会话，包含当前聊天：这里保留为中控台，方便你随时下指令、查进度；另外两个分别负责方案决策与验收、实现与验证。中控建议使用 GPT-6 Luna 或其他经济模型，关键方案交给更适合复杂判断的模型。你想选 3 个、精简为 2 个，还是自定数量？”配合简短选项：3 个（通常推荐，固定中控入口）；2 个（将中控并入方案决策与验收，少一个独立入口）；1 个（自行完成并自查，没有独立验收）。这是总会话数，不是在当前聊天之外再新增该数量。模型已明确时，第二轮可说明由谁承担各项职责，但须等用户选择后再绑定。推荐按项目和已有选择调整，用户自定数量优先；有原生选项工具时将当前推荐放首位。用户未答保持待定，已明确数量则直接采用。只选一种模型也可用同型号多个会话，不强制所有候选都使用。中控模型是推荐而非实际切换；让用户按应用支持的方式选择，不能声称提示词已改变模型。项目资料不足时先说明按一般项目建议，后续只补问影响分工的目标与位置，不倒回第一轮。会话总数与同时模型调用数分开，沿用全局并发约束。
3. **第三轮选择是否额外限制并发。** 会话数量确定后，问：“是否需要为这个项目设置最大并发数？并发数是同一时间正在进行的模型调用数量，不是已打开的聊天数量。如果中转站有并发额度，建议按额度设置；使用 OpenAI 官方账号、没有额外并发控制需求时，可以选择不限制。”提供“不限制：沿用当前环境和已有配置”“设置上限：填写最多同时进行几个模型调用，例如 2 个或 3 个”。不宣称任何官方账号没有限制，不把不限制解释为取消既有限制；仅针对上限的提问不调用收费或模型接口。用户选择设置但未提供数值时再补问，必须为正整数，不默认接受示例。用户明确表示不知道是否需要限制、不清楚额度或先用默认值时，采用“不限制”，告知“先沿用当前环境和已有配置，之后随时可以设置、修改或取消本项目额外上限”，记录该选择依据，不追问不必要的额度信息；用户已明确要求设置限制、仅不知道数值时，先澄清或提供建议，不擅自取消其限制意图。每次提问都简短提示“不确定可以先不限制，之后随时调整”。已明确选择则复用，尚未回答保持待定；沉默不等同于不知道或选择默认值。默认记录为本项目合计上限；用户说明是某个共享中转渠道的额度时，记录涉及的渠道和参与会话，但不索取密钥。调度取项目上限、已知渠道额度和已有全局规则中更严格的限制；角色、子代理及可见的审批或后台模型调用一并计入相应范围，给审批和后台调用预留名额，超额排队。无法观测其他独立会话或跨进程请求时说明统计范围与限制，保守调度，不能宣称已实现全局硬限流。配置与绑定消息须能查到该选择；选择不限制时不再追问数值。
4. **按模型、数量、并发选择和任务安排分工。** 用下表给出最小充分方案，列明每个角色的请求模型、职责、交付、验收关系及兼任情况。优先把关键方案、架构取舍和重大问题裁决交给用户候选中更适合复杂推理与判断的模型，常规实现交给能胜任任务且完成成本合适的模型；执行者先调查并提出方案建议，决策者按关键节点确定方向和约束，不逐步代写实现。依据可核实能力、用户经验与项目需求安排，不按厂商名称固定分岗，不凭价格或型号后缀推断能力。资料不足时说明推荐依据有限，保留用户所选模型。不为了凑齐角色增加模型、会话或并发；未选用的候选说明按需备用，不擅自增加数量。
5. **保存方案并交给绑定流程。** 补齐影响分工的项目目标与路径，按[最小配置](#最小配置)保存待绑定记录，再按[角色绑定与权限](binding.md)生成消息、核实回执并完成配置。未完成的选择保持待定，不用配置代替事实。

| 基本角色 | 职责与交付 | 模型选择与兼任 |
| --- | --- | --- |
| 中控台 | 接收用户指令、维护配置与状态、分派任务、跟踪依赖、转交决定和汇总进度 | 推荐 GPT-6 Luna 或其他经济模型；三会话方案复用首次配置入口，按需工作 |
| 方案决策 | 确定关键设计、裁决规格和公共接口、处理重大问题 | 交给更适合复杂推理与判断的模型，默认兼实现验收 |
| 实现 | 在约定范围完成代码、文档、研究或其他产物，执行必要验证并交付证据 | 按实际任务选编程、写作、资料分析等能力合适的模型；只有独立模块和并发余量确有需要时才增加执行者 |
| 验收 | 根据规格独立核查交付与证据，给出接受、退回或部分接受结论 | 选择能理解任务并发现反例的模型，可与实现者同型号；独立验收须由不同执行会话承担，不能由实现者自称独立验收 |

通常先建议三个会话：中控台、方案决策与验收、实现与验证。当前首次配置入口可作为中控，用户接受后记录绑定；另外两个由用户发送角色消息绑定。中控维护权威配置与台账，接收用户新指令、分派已明确任务、汇总进度及转交结果，不自行改写技术决定或验收结论。它不是额外的旁观者，也不重复调查全部工程或长日志。

中控优先推荐 GPT-6 Luna 或其他能胜任调度、记录与简短汇报的经济模型；是否可用及实际费用以用户接入为准，不硬编码最低价。保留当前聊天需要用户自行选择其模型，不能通过提示词改模型；实际模型无法核实就注明。方案决策与验收交给更适合复杂推理和重大判断的模型，实现与验证交给合适的执行模型。例如中控 GPT-6 Luna、方案决策与验收 GPT-6 Astra、实现与验证 GPT-6.1 Sol；这是组合建议，不按型号跨项目强制分岗。

两会话时把中控职责并入方案决策与验收，另一会话实现与验证；在用户认可后明确哪个真实会话是固定入口，不保留未计入数量的第三个活跃中控。单会话可以实现与自查，没有独立验收。更多执行者只在独立模块和并发余量确有收益时增加，需由用户选择。已绑定项目不因默认建议改变而自动重排。

启动前核对中控与其他角色之间的沟通授权和实际报告接收方；尚无直接沟通授权时集中补问一次，可问“是否允许这三个会话就本项目互相传递任务、问题和结果，由中控集中向你汇报？”选择人工转交时如实说明限制，不把选定三会话当作直接通信授权。中控随用户消息、真实交付或阻碍事件工作，不要求常驻运行或持续轮询；用户随时可来询问，但进度须有读取时间与可核对来源，不能把旧摘要当实时状态。

执行者可以调查、提出方案建议，自主处理常规细节；关键方向、公共接口与重大范围取舍交决策者裁决。独立实现验收由不同执行会话承担。方案制定者可以验收他人实现，但不构成对方案本身的独立复核；用户要求方案独立审查时，须安排未参与制定的审查者。会话和调用数量遵守已有全局约束，不默认同时运行全部会话。

## 效率与费用取舍

以完成合格任务的总耗时和可观测总费用为依据，包含重复上下文、工具失败及返工，不承诺某种组合始终最快最便宜。结合用户的订阅额度或按量计费方式提出建议；不清楚价格或用量时写未知，不编造节省比例。只在会影响当前选型时补问质量、速度与费用偏好，不把费用调查变成首次绑定的前置问卷。

把能处理约束和复杂问题的模型用于方案取舍、困难根因与关键验收，主力模型自主完成常规实现；清晰的小任务可交合适的快速模型，但不为微小工作额外开会话。模型强弱与完成成本依据可靠资料、用户经验或少量同条件项目样例判断，不仅看品牌、代际、单价或输出速度。

协作优先用短消息通知，权威规格、决定和证据放共享记录；代码并行按需用 worktree 或已有独立工程。协调者在启动、实质变化、阻碍或整合时介入，验收者在有可验收交付或关键风险时工作，不为持续在线消耗轮次。普通细节由执行者自主处理，相关小任务合批交付、按风险验收；不省略必要验证或用户要求的独立复核。运行时的信息流、等待与增量读取见[执行与验收](orchestration.md)，不另建摘要角色或重复台账。模型指南仅在选型或变更模型且需要依据时读取，不随每项任务加载。

## 最小配置

明确当前任务需要的目标、输入或工程基线、用户选定角色与模型、职责边界、会话映射、沟通授权及验收标准。已有选择直接复用，只集中询问影响当前动作的缺失项，不把模板所有字段都变成启动前置条件。

区分四件事：角色定义职责，会话提供执行位置，模型是宿主运行配置，任务是可交付工作。记录用户请求模型与已核实实际模型；提示词不能修改模型。工具不支持用户所选配置时如实说明，不静默替换。

每个角色契约包含目标、范围、自主决定事项、可写文件、升级对象、交付物和验收人。规格裁决、公共接口、分派、整合和最终验收可由同一角色兼任；不为常规实现安排逐步审批，单角色自查不称为独立审查。用户认可的模型分工应按任务难度与错误代价使用，需要超出已认可策略时才请求调整，不强制先用低成本模型试错一遍。

采用满足依赖的简单模式：相互依赖任务顺序执行；有公共裁决与多个独立模块时由管理者协调；模块独立实现、公共部分串行整合时采用混合模式。不要为选择模式新增角色。
