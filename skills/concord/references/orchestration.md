# 执行与验收

用于接收分派、内部裁决、独立实现、验证、交付和整合。先读项目配置、本人角色契约、当前任务及最近生效决定；暂停项目仅执行用户明确授权的例外范围。

## 1. 接收有效任务

任务应明确ID、规格版本、分派序号、执行负责人、验收人、工程与基线、可写范围、依赖及放行条件、预期产物和验收标准。规格缺口影响行为或依赖未满足时先提交事实、影响与建议，不自行补猜。

核对当前分派和文件归属后发送真实 `ACCEPT`。未回复、工具送达、等待超时都不能代替接收或批准。收到同一任务/版本/序号的重复消息时引用已有处理结果，不重新启动任务、服务或扣除资源。旧分派对照当前记录，不覆盖新状态。

推荐状态流：草拟 → 待裁决 → 就绪 → 已分派 → 执行中 → 待验收 → 已验收 → 已整合。退回后进入需修复；等待原因和覆盖范围单独记录。无需整合的任务以验收为终点，暂停状态见[恢复规则](recovery.md)。

## 2. 沟通与裁决

消息至少包含项目、消息ID、类型、发送与接收角色、任务ID、规格版本/分派序号、记录路径及所需动作。类型使用 `ASSIGN`、`ACCEPT`、`QUESTION`、`DECISION`、`DELIVER`、`REVIEW`、`HANDOFF`；具体模板见[记录模板](templates.md)。

常规细节自行处理。行为歧义、公共接口、兼容承诺和范围取舍提交给指定裁决者，包含事实、证据、最小方案、影响和可继续的独立工作。裁决者将有效决定写回规格；实质变更提高规格版本，通知受影响负责人，说明旧证据复用范围。

有界等待回复，单次通常不超过60秒；无变化时减少轮询。不重复发送同一问题，不把超时视作失败或批准。传输失败先检查真实状态；外部写入结果不明先确认是否已经发生；不自动重试有重复副作用的动作。

发送报告前核对配置中的实际接收方和直接用户授权。自动审批拒绝时记录动作、接收方与原因，不变换措辞或转发路径绕过拒绝。有允许的只读会话访问时可核实实际结果，并注明取得方式；否则保留待授权回报状态。验收已完成与回报未送达分别记录，不能声称失败消息已经送达。

### 同会话的多个任务

收到直接用户新消息，先判断是当前任务的补充、兼容的独立任务，还是明确替换/取消。补充并入原任务；独立任务保留各自ID、状态和边界；明确替换/取消则停止旧任务推进并保存必要交接。无法判断且影响行动时才澄清。

切换前记下等待原因、已完成工作和下一步。等待外部输入时可推进不依赖它的独立任务；不能兼顾时向已授权调度方说明待处理，避免其他角色反复等待。不要把等待算完成、频繁催促或为此增加代理；只读任务也不能因切换到新任务而自动获得写入权限。

## 3. 实现与证据

冻结提交SHA或不可变源码包及SHA256，版本名称不能唯一标识基线。默认在独立分支、worktree或工程副本实现；只有明确委托才改主工程。每批默认一个行为与验收清晰的功能，用户另定粒度则遵从。

先识别现有实现、依赖与未知项，再在约定范围内完成最小改动。用真实行为和有意义的边界验证；编译通过和进程退出0不能代替案例完成。按风险核查资格、失败、取消、清理、生命周期和兼容影响，不添加只复述实现的测试。

证据绑定实际源码、构建产物与运行输入。新改动重跑受影响检查；复用旧结果说明未受影响的范围和依据。区分通过、失败、未运行与跳过。保存失败及修复关系，不能放宽断言使记录通过。

结果可疑先核对证据；确有必要时针对同一子代理任务重派一次，不反复重派。额度不足或收益低时由负责人独立完成，不绕过运行上限。

## 4. 交付、验收与整合

执行者提交 `DELIVER`：机制、源码/补丁及修改清单、实际证据身份、运行环境与日志、结果、限制、未验证项，适用时附不可变产物与校验值。只读或方案任务按其规格交付，不额外编码或生成项目文件。

验收人发送 `REVIEW`，按规格判定接受、退回或部分接受，并说明接受范围、遗留项和依据。角色只能更新自己有权推进的状态；交付不等于验收，自查不冒充独立审查。接受局部演练不代表接受项目功能或整个项目。

整合负责人核对基线漂移与文件冲突，合并最小补丁并执行受影响检查。行为选择不明交指定裁决者。记录新基线、产物和证据，保留已验收检查点；打包排除缓存、联接和临时世界递归。

统计绑定当前任务/功能目录的分母，分别报告实现、验证、验收、整合及部分完成。当前批次结束后按总目标继续；仅全部必需成果验收和整合后才能宣布项目完成。
